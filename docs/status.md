# Status

**3.7.0**, 2026-11-25. What shipped is in [CHANGELOG.md](../CHANGELOG.md), what's next in [todo.md](todo.md), and the engineering log up to 2.13.0 in [archive/status-log.md](archive/status-log.md).

Every change runs `npm test` (1133 tests at 3.7.2, including the real PTY host driven with `/bin/bash` and two real Syncthings syncing with each other) on Node 22, 24 and 26, the typecheck (the TypeScript, and the terminal host, `vibeforge tell` and the phone page through JSDoc), lint, an audit of what ships, the coverage floors (85% on `src/core` and `src/shared`, and one per file), `scripts/smoke.mjs` on the built app, and the end-to-end scenarios in `e2e/` (`npm run e2e`: the built app on a scratch profile with stand-in CLIs; seven scenarios, among them Viby's typing and "go", a task's copy discarded and brought back with Undo, and lists that can't be read). CI runs all of them on each pull request and on `main` (the two-Syncthing test once, on Node 26), the smoke test and the scenarios under `xvfb-run`, keeps the reports and, when something fails, a screenshot, the page and the logs, and retries a test listed in `tests/flaky.json` once while still reporting it; it also packs the ready-made build, installs it into a scratch home and runs the smoke test from there. A nightly run on `main` and on each push to a `release/` branch repeats the tests on arm64 and on Ubuntu 24.04 with the newest Node patches, packs both archives, and tries `npm update`; a weekly run lists the tests that failed or needed a re-run in an issue; the Release workflow publishes a tag only once those checks passed on its commit on `main` (since 2.16.0 in two jobs: a build with a read-only token, then a publish that attests the build), and has published every tag from 1.3.0 on, except v3.3.0, whose pack step failed on arm64 and whose changes shipped in 3.3.1. Features are then driven in the built app over CDP with a scratch profile.

## Known limits

- Claude Code asks you to trust each new folder once, so a new chat's first message waits for that answer in its terminal.
- Allowed folders are a policy in the prompt, not a sandbox.
- A first prompt passed on a CLI's command line can be read by other user accounts on the same computer (`ps`, `/proc`) while that CLI runs.
- No token counts from Cursor Agent or Crush: neither keeps per-call counts that can be added up.
- Turning the tray off applies from the next start. Electron names every tray item `chrome_status_icon_1`, so a pin can also catch another Electron app's icon.
- Which terminal handed out which task lives in memory: after a restart a lead CLI can't `vibeforge apply` tasks it handed out before (Apply on the task still works). Tasks and routines waiting for their folder are kept in `waiting.json` and survive a restart.
- Viby's (formerly Maestro's) checkouts made before 2.14 (`<project>.worktrees/<branch>`) get no Apply or Discard; remove them by hand.
- The phone page buzzes only while it is open; a locked phone would need Web Push.
- Sync: a synced agent or skill goes to every paired machine; there's no picking which. Its brief, memory and skills from a paired machine become part of its prompt here, so pair only machines you trust.
- Sync: a paired machine can narrow a share but never widen it (both ways where you chose one, or `.git` where you chose files only); it asks, and you change it in Settings → Sync. Two-way sync of a workspace still means the other machine's files arrive here, including ones that run code when you work in the folder (package scripts, `.envrc`, a CLI's own settings), so pair only machines you trust.
- Sync: a workspace syncs with one other machine. A synced workspace is one checkout on two machines: when they were on different branches while apart, the branch switched to last is the one both end up on (the other's commits stay on their branch). With a firewall on both machines and neither opened, they can't connect: Settings → Sync shows the command.

## Risks

- **The CLIs change under VibeForge.** Prompt flags, session-log formats (Viby's read/reply lookup, `--wait`, token counts) and the plan-limit endpoints (Claude's OAuth usage, Grok's billing, Kimi's usages) aren't stable public APIs. Grok Build updated itself mid-trial in 2.11 and added a trust question. The model and effort options Viby passes (2.16) were read from each CLI's `--help` on 2026-11-12.
- **Plan limits use the CLIs' saved sign-ins.** They're only read, never renewed, but a provider could object. That is one reason the feature is off by default.
- **Dependencies.** `npm audit` on 2026-11-12: no advisories, with or without dev tools, on Electron 45, Vite 8, Vitest 5 and TypeScript 7. CI fails on a high-severity advisory in what ships, and Dependabot proposes updates weekly. Electron 45's tray, voice and notifications were checked only through the headless smoke and stand-in drives, not on the real bar.
- **The control socket trusts the OS user boundary.** Each launched pane receives a random per-PTY capability token (`VIBEFORGE_PTY_TOKEN`) verified with constant-time comparison (and pane ids without a registered token are refused), requests are token-bucket rate-limited per PTY and for external `"outside"` callers, the socket caps concurrent connections (`maxConnections = 64`), and hand-off caps are enforced before task files are created. Other processes running as the same Linux user can still inspect `/proc/<pid>/environ`, which is an OS user-boundary property rather than unauthenticated socket trust.
- **Syncthing underneath.** Sync drives Syncthing's REST API and reads the names it gives conflict copies; both were read from 2.1.7 on 2026-11-17 and are checked by the two-instance test on every change, so a bump that breaks them fails there. `.git` is synced file by file: git's own commands on both machines within the same seconds can still leave a conflict copy inside `.git`, which the rescue then sorts out (commits are never lost; staged-but-uncommitted state can be).
- **One machine.** Most live manual verification ran on the founder's Omarchy desktop; `scripts/install.sh` now detects `pacman`, `apt-get`, `dnf` and `zypper`, and `.github/workflows/release.yml` builds and smoke-tests both `linux-x64` and `linux-arm64` archives.
